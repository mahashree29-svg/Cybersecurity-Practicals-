# Practical 1 — SET Credential Harvester (LAN Delivery)

## 1. Objective

Understand how the **Credential Harvester Attack Method** in the Social
Engineering Toolkit (SET) works on a local network: what each component
does, what makes the technique effective against humans, and what controls
defenders deploy against it. Pair the concept with the corresponding
detection and prevention surface.

---

## 2. Background

### SET in one paragraph
SET (Social-Engineer Toolkit, by David Kennedy / TrustedSec) is a Python
framework that packages common social-engineering attack patterns —
credential harvesters, payload generators, mass-mailer flows, web-cloning
modules — behind a menu-driven CLI. It is built for authorized red-team
engagements; the same properties that make it useful in those engagements
make it dangerous outside them.

### What "credential harvester (LAN)" means
The LAN variant of the credential-harvester pattern has three pieces:

1. **A look-alike login page** generated by cloning the HTML of a real
   site and rewriting the form action to point at a local listener.
2. **A local web listener** that records POSTed form fields.
3. **A delivery mechanism on the LAN** — typically DNS spoofing (so a
   victim typing `mail.company.local` lands on the attacker host) or a
   crafted link sent over chat/email inside the segment.

The attacker never compromises the real site. The deception is entirely
client-side and entirely human-targeted: the victim sees a familiar
login screen and types real credentials into a form whose `action`
attribute points at the attacker.

### Why the technique works on humans
- **Visual fidelity.** The cloned page is byte-identical above the fold.
- **Trust transfer.** Users trust the *appearance* of a site more than
  the URL bar.
- **Context priming.** A LAN attacker often controls the delivery
  context too ("IT is doing maintenance, please re-login at this link").
- **Padlock confusion.** Pre-HSTS, users were trained to look for the
  padlock; a plain-HTTP clone often slipped through. Modern browsers
  show "Not Secure" prominently, which materially reduces success.

### Why LAN delivery is a meaningful sub-case
- DNS spoofing on the local segment lets the attacker hijack a known
  hostname the victim already trusts, sidestepping the URL-inspection
  defence.
- Internal phishing tends to bypass the email-security stack that filters
  external mail (no SPF/DKIM/DMARC check on a Teams DM or an internal
  Slack message).
- Defenders often under-monitor east-west traffic on user segments.

## 3. Detection

| Signal | Where to look |
|---|---|
| Unauthorised HTTP listener on a user-segment host | EDR (process telemetry: `python`/`setoolkit` binding :80/:443), network scans |
| ARP / DNS spoofing as the delivery primitive | arpwatch, DNS query logging, IDS rules (Suricata `dns-events`) |
| Authentication from an unusual user-agent / IP for a known account | Identity-provider risk signals (Entra ID Conditional Access, Okta ThreatInsight) |
| Multiple authentication attempts within seconds of each other from different IPs | SIEM correlation on auth logs |
| User-reported "weird login page" tickets | Internal phishing report button |

The single most effective detector is **a fast, low-friction user-report
channel** — most credential-harvesting campaigns are caught by the first
suspicious user, not by the SIEM.

## 4. Prevention

### Identity layer (defeats the attack outcome)
- **Phishing-resistant MFA** — FIDO2/WebAuthn passkeys. A harvested
  password without a matching authenticator is useless. SMS / TOTP /
  push-notification MFA can still be phished (real-time relay), so this
  is the specific control that matters.
- **Conditional Access** binding sign-in to managed devices and known
  locations.
- **Token-binding / DPoP** where the IdP supports it.

### Network layer (defeats the LAN delivery primitive)
- **Dynamic ARP Inspection + DHCP snooping** on access switches.
- **Encrypted DNS** (DoH/DoT) at the client, ideally pinned to a
  corporate resolver.
- **Internal DNS** answers reviewed for unexpected `A` records pointing
  to user-segment IPs.

### Endpoint / browser layer
- **HSTS preload** on every owned web property.
- **Browser Safe Browsing / SmartScreen / Defender for Office URL detonation.**
- **Workspace identity for SSO** so users rarely see standalone login
  forms — anything that *does* look like one becomes suspicious by default.

### Human layer
- **Phishing simulations run by the security team** with consent and a
  no-blame outcome — to give users repeated, safe exposure to the
  pattern.
- **Report-phish button** in mail and chat clients.

## 5. Modern Relevance

The mechanics SET demonstrates (clone HTML, rewrite form action, harvest
POST) are unchanged since the early 2010s. What's changed is the
*context*:

- LAN delivery via DNS spoofing is far less reliable than it was — DAI
  and DoH have closed the easy paths in well-managed networks.
- The high-value sites users authenticate against (M365, Google Workspace,
  Okta) are HSTS-preloaded, so the cloned page can't credibly pretend to
  be the real domain over HTTP, and a different domain over HTTPS is
  visible in the URL bar.
- The credential-stealing payoff itself has been blunted by
  phishing-resistant MFA on those same platforms.

The net effect: the attack is now most effective against **smaller
internal apps** that don't have SSO, MFA, or HSTS — and that's exactly
where defenders should concentrate hardening.
